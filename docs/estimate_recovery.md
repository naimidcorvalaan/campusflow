# 非常规任务估时兜底

本轮没有真实调用 TJU，也没有保存此前申请表的原始模型响应。因此不能确定那次具体失败字段。
代码中能确认的原因：完整材料解析要求每项全部字段合法；一次修复仍失败时，以前会整体丢弃结果，包括其中合法的估时。

现在文字、图片、DOCX、文本 PDF 和视觉 PDF 共用同一个恢复边界：

- 完整合法：原流程、原事实门禁不变，通常一次调用。
- 独立行为估时：`actionability` 与 `estimate` 不依赖正式 `items`；可填写字段本身支持填写意图，不要求额外出现“请完成”。`items=[]` 时一次调用即可展示估时；items 类型或正式材料外层结构损坏时也可保留有证据的估时，但禁止快捷转正式任务。
- 完整结构失败：仍最多一次格式修复。随后从已有的合法 JSON 中读取明确的估时字段；不读取自由文本数字，不新增调用。
- 可估时：展示“先给你一个时间估计”，不是正式任务成功。估时只含名称、简短范围、区间、建议分钟、依据及假设；整数 1–1440 分钟且区间自洽。
- 估时也不合法、无任务意图或没有返回：不编造时间，请用户补一句具体要做什么。

## 加入计划

仅当单一任务的原结果明确没有时间、地点、固定安排、疑似已有任务或不确定事项时，提供简短确认。
用户确认“新任务、非固定安排、无截止或指定地点”，确认名称和分钟后，才生成最小任务草稿。
随后仍必须点击“确认并加入计划”，走原有完整批次校验与原子发布。
来源保留为用户确认，并在草稿依据中注明来自未完整整理结果的估时；不伪装为完整解析成功。

有约束、字段缺失或多事项中的估时项只展示估时，不提供快捷转正式任务。
已合法事项可按原流程勾选确认；未理解项不进入正式批次。
正式事实不拼接不同响应，也不自动合并已有任务。仅对名称与范围完全一致的单项任务保留首次合法估时，避免格式修复丢掉已识别工作量；不覆盖材料明确写出的用时，不转移截止、地点或已有任务引用。

“重新估算”只有用户点击后才复用现有任务估时调用（最多一次修复）；不会重新上传原文件或偷偷重读图片。
修改、勾选、生成最小草稿不调用模型。最终加入沿用原规划重建，可能有既有规划调用，但不会重新理解材料。

## 真实路径失败后的状态链修正（2026-09-11）

本节替代上轮关于“成功后自动折叠补充输入”和“所有空结果均表示需要用户说明意图”的行为。保留前文作为进度历史。

### 查明的问题

没有保留用户那次真实模型的原始响应，因此不能断言它返回了哪一个具体字段。此次先在修改前的代码上构造等价回放：文件名/正文为综合素质测评表，有可填写评分栏及复杂内容；模型首轮返回合法外层 JSON、空正式 items、没有独立估时。完整跑过上传、明确补充“填表”、处理前中后，并保存了实际浏览器证据。

- 原提示词前半段要求部分可读也估时，末尾却仍写“看不清、裁切、缺页或范围不明时……只提出一个问题”；“时长只提材料明确值”也没有限定到正式 `items.minutes`，与工作量估计混淆。
- `finish_result` 对合法空 items 只在 `actionability.is_estimatable=true` 时才要求修正。缺少 actionability 或返回 false 的空结果，首轮就直接进入 needs_input，没有使用尚可用的第二次调用预算。
- “填表”确实会进入 `MaterialDraft.supplemental_context` 和请求 JSON。旧路径回放实际记录为：无补充首轮 `null`，第二次点击首轮为 `填表`；两次点击都各调用一次就结束，均没有估时。它并非根本没传入模型，而是空结果被提前接受、后续用通用文案重复追问。
- 旧 textarea 的 `value` 使用不断写回的草稿补充值。Streamlit 1.31 的 `compute_widget_id` 把默认 value 算入组件标识；同一 key 的默认值变化仍会创建新标识。结果槽又在输入区之前增补内容，长请求期间旧组件未清理，形成两套输入。修改前连续 10 次处理中采样均为 **2 个** textarea，实际截图包含两套“补充说明 / 填表 / 帮我看看”。
- 成功处理（包括被误当成成功的空结果）后显式设置 `extra_open=False`，所以输入区无论用户是否仍在使用都会消失。旧 DOM 组件清理与默认值变化进一步让用户感到补充丢失。

### 当前状态流

`输入 → 冻结本次提交快照 → processing → result / needs_input / error`

- 一个 `cf_material_flow` 管理交互阶段、编辑内容和当前待处理请求；结果仍由原 MaterialInbox 持有，正式任务状态与门禁不变。
- 点击只提交一次快照并 rerun；下一轮先完成 processing 界面的渲染，再消费快照并调用服务。已消费的请求不能因另一轮 rerun 自动再次发出。处理中输入禁用，提交数据不依赖会变动的 widget 值。
- 材料区域使用一个 `st.empty` 表面整体替换；textarea 从 session state 初始化一次，之后不再反复改变默认 value。组件位置变化不会在长请求中留下上一轮输入副本。
- 补充区由用户控制开关，完成后不会自动折叠；补充文字单独保存在交互状态中，手动收起/展开也保留未提交文字。
- 材料调用统一经过同一个分派器及响应解释入口。第一轮没有可用估时时，使用原本的第二次调用预算完成估时，而非继续纠结正式 items；第二轮明确使用原材料、已选图像页和同一份补充说明，要求只估可识别部分。已有合法估时而正式结构损坏时仍保留原结构修复路径。总上限仍为 **2 次**，没有新增分钟规则或第三层兜底。
- coverage 仅限定时间覆盖范围，不删掉合法分钟。只有有材料证据的纯参考响应且用户没有说明动作时才追问意图；没有产出合法估时或已经说明动作却仍返回空结果，标为 `estimate_unavailable` / error 并保留材料及补充，不再声称用户没说明要做什么。合法正式事项仍保留原校对能力。

### 已复现的问题与修复

- Word 读取器只遍历正文的直接段落、直接表格，单元格又只读取直接段落。内容控件包住的表格和嵌套表格字段会被跳过。新的空白表单样本不含“填写”祈使句，旧代码实际只读到标题，读不到姓名、评分、约300字自我评价、证明等工作量。现在按顺序展开内容控件、递归读取嵌套表格，保留实际空单元格标记；普通内容控件不再被误报为不可读复杂内容。图片等仍保留覆盖限制。
- 首次请求的文字要求先估时，但 output 中仍摆着完整正式事项模板。现将 output.items 默认设为空，正式事项格式独立为可选项；第二次补全请求完全移除正式事项格式。工作量估时始终依据读到的字段、写作、回忆、查找证明和复核，不新增固定分钟或文件名规则。
- 独立估时与条目估时都把 clarification_question 当作否决开关，连同时存在的合法区间、依据和假设一起丢弃。现在这些估时可以作为部分结果展示，但关闭快捷转任务资格，并强制保守覆盖；无证据、无有效区间的响应仍不能产生分钟。工作量引用仅容许排版空白归一化，正式时间与任务事实校验不放宽。
- 响应恢复按事项数量选择，可能用首轮多个无用时事项压过第二轮的可靠估时。现在优先保留可用工作量；已经校验的正式事实另行保留，只在名称与范围精确且唯一匹配时附加估时，其他估时不能借此越过正式确认。
- 不可用结果与纯参考材料不再共用“准备怎么处理”的文案。已有补充说明或上传材料附带的用户说明时，失败只说明本次未得到可靠估时，不重复询问意图。
- 浏览器连续帧复现了两套“填表”输入与按钮，旧组件带 data-stale=true。仅用 st.empty 包住整块入口不足以解决，并会重建展开区。现在保持展开区和输入区位置，来源与结果容器始终有固定占位，操作列结构固定；已有的请求快照、最多两次调用、补充文字独立保存机制继续使用。
