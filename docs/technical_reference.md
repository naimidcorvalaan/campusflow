# CampusFlow

> tjuer专属的校园时空规划系统

CampusFlow 帮你回答：

> **“我现在这段时间最值得做什么？”**

直接说一句今天想做的事，就可以开始。不必先整理任务表、逐项算时长，或先填完个人设置。

## 最快开始

1. Windows 安装 Python 3.12（已有兼容环境可直接用），解压项目后双击 **`启动 CampusFlow.bat`**。
2. 首次启动会准备独立环境和依赖，随后自动打开浏览器；之后启动不重复安装。使用期间保留启动窗口。
3. 在“今天还有什么事？”写一句话，点“帮我安排”。默认北洋园、步行、当前时间，位置可留空。

尚未配置模型也能打开页面。生成真实计划需先完成下方的本机模型配置。
启动问题、日常使用与开发验证见 [本地启动说明](local_quickstart.md)。

## 和普通 AI 日程表有什么不同

- **校园移动一起算**：基于高德地图数据的本地校园图，把通勤、收拾、到楼和到教室时间算进计划。
- **执行变化后继续调整**：告诉它剩余工作或位置变化，更新接下来的安排；也能先预演再采用。
- **任务工作量可估算**：不知道多久，可以确认任务范围、补充个人情况、修改采用分钟，再加入计划。
- **设置一次，以后少输入**：开启个性化后保存课表、常用地点和偏好；以后生成计划时自动考虑当天课程。本次明确要求优先。

## 三个使用场景

- 第一次用：“晚上七点有课，课前想吃饭，还有高数作业想做一点。”先安排能执行的部分，必要时只突出一个待确认问题。
- 已保存课表：“下午想把作业做一点。”不必每天重输课程；未知工作量保留暂估来源，已确认分钟不会被重估覆盖。
- 计划变了：“作业还剩40分钟，我现在到图书馆了。”继续调整当前方案；“先给我看看”会进入预览，采用前不改正式方案。

## 直接整理通知

老师通知不必先改写成计划：在主输入下展开 **“难以估计任务时间？让campusflow帮你估”**，写一句任务、粘贴原文或上传任务图片并点击“帮我看看”。
同一次结构化调用整理范围、截止、不确定性和粗略用时；补充情况后可主动重估，确认前不改变正式计划。
疑似已有任务会要求选择补充还是新建。选中需要处理的事项，点击 **“确认并安排”** 才会加入并更新方案。
复制来的“下周三”没有可靠通知日期时会保留待确认，不按电脑日期猜。
个性化档案可恢复最近的文字草稿；匿名草稿仅在当前会话中保留。
当前材料固定安排只加入对应规划日；其他日期先保留待处理，不自动跨天规划。
使用边界和离线证据见 [文字材料说明](material_inbox_delivery.md)。

## 本机模型配置

模型服务配置属于这台电脑，不属于个人档案。把 `.env.example` 复制为 `.env`，填写学校提供的
`TJU_LLM_API_KEY`、`TJU_LLM_BASE_URL`、`TJU_LLM_MODEL`，然后重新双击启动。
不要把密钥填在任务或个人设置里；`.env` 已排除在 Git 外，不能随项目发给同学。
本轮提供明确引导，没有在页面增加密钥输入或保存功能。

当前主要是本地 Web 应用；TJU 服务需要满足学校提供的网络/VPN与账号使用条件，校外网络可达性以实际服务为准。
地图是本地静态数据，不提供实时路况或跨校区交通。当前图片接口已用合成图真实验证，复杂任务图与二维课表仍需用户确认。
匿名模式可直接规划，但不承诺关闭浏览器后的恢复；持久档案需用户主动开启。学号是档案标识，不是身份认证凭据。

无需 API 的排练见 [3–5分钟演示指南](demo_guide.md)。离线演示标注合成数据，使用临时档案，不代表真实模型效果。
开发、认证和部署原型资料见 [开发与运行边界](deployment_readiness.md)。下面保留已有详细能力与实现记录，便于查阅。

## 1. CampusFlow 能做什么

用户可以直接用自然语言描述接下来的安排，例如：

```text
我想在图书馆写一会儿实验报告，然后吃饭，
今天21:00去9教上课，一个半小时后下课。
然后写一个小时作业，还想背单词，还需要洗20分钟衣服。
```

CampusFlow 会尝试识别：

- 地点型任务，例如“在图书馆写实验报告”；
- 普通学习任务，例如“背单词”；
- 吃饭等校园生活任务；
- 明确时长，例如“写一个小时作业”“洗20分钟衣服”；
- 固定安排，例如“21:00 去9教上课”；
- 相对时间，例如“一个半小时后下课”；
- 用户表达出的任务顺序和优先级。

随后结合所选校区的校园地图、步行路线和时间约束，生成一份可执行的当前方案。

例如：

```text
现在：写实验报告

19:37–19:45  步行去学三食堂【已为您选择就近食堂】
19:45–20:25  吃饭 40分钟
20:25–20:46  修整一下
20:46–20:50  步行去第九教学楼
20:50–20:55  进楼找教室
20:55–21:00  课前准备
21:00–22:30  上课
```

如果用户随后说：

```text
我现在就想洗衣服
```

CampusFlow 会重新理解用户的最新意图，在不破坏课程、路线等硬约束的前提下重新规划，而不是简单沿用旧计划。

## 2. 双校区校园地图

CampusFlow 当前支持天津大学两个校区：

- **北洋园校区**
- **卫津路校区**

用户在页面中明确选择当前校区。

CampusFlow 不会让大模型自动猜测校区，也不会在解析失败后偷偷跨校区寻找同名地点。

对应的静态校园地图数据位于：

```text
data/
├── beiyangyuan_map.json
└── weijinlu_map.json
```

地图中维护校园 POI、道路与可通行拓扑。

系统可以在选定校区内完成：

- 建筑名称解析；
- 别名解析；
- 当前地点解析；
- 任务地点解析；
- 食堂候选选择；
- 步行路线计算；
- 校园内不同地点之间的连续移动规划。

路线由程序基于校园图计算，而不是让 Qwen 猜测“走几分钟”。

## 3. 真实校园移动

CampusFlow 将校园移动作为正式规划事实，而不是生成方案后的装饰文本。

例如：

```text
图书馆写实验报告
↓
收拾东西
↓
步行去食堂
↓
吃饭
↓
收拾东西
↓
步行去教学楼
↓
进楼找教室
↓
课前准备
↓
上课
```

系统会为这些移动预留真实时间，并重新计算任务可使用的时间窗口。

地点绑定任务同样受到执行地点约束。

例如：

```text
在图书馆写实验报告
```

一旦用户已经离开图书馆前往食堂，剩余的实验报告不能被规划器继续塞到食堂后的时间段中。

对于这类任务，CampusFlow 会使用任务执行地点和首次离开该地点的时间作为正式分配边界。

---

## 4. 课程前准备

CampusFlow 对课程采用固定的校园执行规则：

- **提前 10 分钟到教学楼**
- **提前 5 分钟到教室**

例如：

```text
21:00 上课
```

规划目标为：

```text
20:50 到教学楼
20:50–20:55 进楼找教室
20:55–21:00 课前准备
21:00 上课
```

这里的 10 分钟和 5 分钟属于程序确定性约束，不交给模型自由修改。

---

## 5. 自动选择食堂

如果用户只说：

```text
然后吃饭
```

而没有指定食堂，CampusFlow 可以结合当前校园位置、前一项任务地点和下一项任务地点，从当前校区已有食堂 POI 中选择合适的食堂。

例如：

```text
步行去学三食堂【已为您选择就近食堂】
```

食堂选择基于校园真实路由，而不是：

- Qwen 猜测；
- 直线距离；
- 写死某一家食堂；
- 跨校区搜索。

用户如果明确指定食堂，则始终以用户选择为准。

---

## 6. 吃饭时间策略

当用户没有明确指定吃饭时长时，CampusFlow 使用一个生活化默认值：

```text
40 分钟
```

40 分钟代表**正常吃一顿饭的优选时间**，而不是必须严格满足的唯一时长。

规划器会综合：

- 去食堂的时间；
- 吃饭时间；
- 离开食堂后的移动；
- 下一项固定安排；
- 课程前准备时间；

决定如何安排。

如果完整 40 分钟不可行，但仍存在合理连续时间，系统可以适当压缩；如果剩余时间确实不足，则不会为了“塞进去”而制造不可信的碎片化用餐方案。

程序默认不会给 `meal_default` 标记“AI 暂估”，因为它属于 CampusFlow 的产品默认策略，而不是模型预测结果。

## 7. 当前地点与位置假设

“我现在的位置”是可选输入。

### 用户提供当前位置

如果用户填写：

```text
31斋
```

CampusFlow 会从该地点开始计算后续校园移动。

### 用户没有填写当前位置

如果后续计划确实依赖路线，而且任务中已经存在可信地点，例如：

```text
我想在图书馆写实验报告，然后吃饭
```

CampusFlow 可以暂时假设用户已经在图书馆，并在当前方案中明确告诉用户：

```text
你没有填写当前位置，我先按你在图书馆来安排。
```

同时提出确认问题。

这是一条显式假设，而不是隐藏事实。

如果用户之后反馈：

```text
其实我现在在31斋
```

系统会将当前位置从 `assumed` 更新为 `user`，删除旧假设，并重新计算移动与计划。

## 8. 持续重规划

CampusFlow 的目标并不是“一次生成一张时间表”。

用户可以随时告诉 CampusFlow 现实发生了变化，例如：

```text
其实我现在在31斋
```

```text
我现在就想洗衣服
```

```text
我还是想先吃饭
```

```text
先写作业再背单词
```

```text
洗衣服还是晚上再做
```

```text
算了，不洗衣服了
```

```text
我已经把衣服洗完了
```

这些反馈可能分别表示：

- 当前位置纠正；
- 当前任务优先级变化；
- preferred next task；
- 任务顺序变化；
- postpone；
- cancel；
- complete；
- restore。

CampusFlow 不直接修改已经渲染出来的旧时间线。

反馈首先更新可靠的 canonical facts，随后从这些事实重新构建一份新的候选方案。

候选方案只有通过完整一致性校验后，才会作为新的 `LiveFinalTurn` 一次性发布。

如果新方案构建失败，系统会继续保留上一份可靠方案，而不是展示一份只更新了一半的时间线。

## 9. Qwen 决策增强

CampusFlow 运行时使用天津大学提供的 Qwen 模型。

模型不是整个规划系统本身，而主要负责程序难以通过固定规则可靠完成的语义判断。

### Initial Intake

初始输入通常经历：

```text
用户自然语言
    ↓
Qwen Raw Event Extractor
    ↓
Qwen Semantic Linker
    ↓
Qwen Semantic Auditor
    ↓
严格结构化校验
    ↓
程序规划
```

Raw Event Extractor 先尽量找全任务、meal、固定安排、地点与时长；Semantic Linker 再把
duration、before / after、meal 与 fixed commitment 等关系绑定到稳定事件。Semantic Auditor
最后检查：

- 是否漏任务；
- 是否漏明确时长；
- 是否漏固定安排；
- 相对结束时间是否绑定正确；
- “然后”等自然语言关系是否被遗漏；
- 是否错误补出了用户没有提供的信息。

例如：

```text
21:00上课，一个半小时后下课
```

Qwen 负责判断：

```text
一个半小时后
```

描述的是上一节课的结束时间。

程序负责完成：

```text
21:00 + 90分钟 = 22:30
```

时间算术不交给模型自由计算。

## 10. FeedbackDecision

针对计划调整，CampusFlow 增加了正式的反馈决策层。

反馈中的任务最终会绑定稳定的 `task_ref`，而不是只保存一段任务标题字符串。

结构化反馈语义可以表达：

- preferred next task；
- priority raise / lower；
- relative ordering；
- cancel；
- postpone；
- complete；
- restore；
- location correction；
- clarification。

例如：

```text
我现在就想洗衣服
```

系统不会只得到：

```text
需要重新规划
```

而会进一步理解：

```text
用户明确希望：
洗衣服成为当前优先任务
```

并将该偏好传入确定性规划过程。

如果用户要求的任务在当前窗口客观不可行，例如距离固定课程只剩 5 分钟，而洗衣服需要 20 分钟，程序仍然优先保证固定承诺，并向用户解释冲突，而不是强行安排。

## 11. 多阶段 Qwen 检查

一次重要 feedback 可以经过多个职责不同的 Qwen Pass。

典型流程：

```text
Qwen A
Feedback Interpreter
解释用户最新意图
        ↓
Qwen B
Decision Critic
检查是否漏任务、错绑目标或理解错误
        ↓
程序
路线 / 时间 / allocation / fixed commitment
        ↓
Qwen C
Intent Compliance Reviewer
检查候选方案是否违背用户刚刚的明确要求
        ↓
LiveFinalTurn invariant
        ↓
展示
```

Qwen 不负责重新计算校园路线或覆盖程序确定的事实。

这种设计允许 CampusFlow 使用更多模型推理能力，同时避免将整个系统退化为一次不可控的自由文本生成。

## 12. 可拆分任务与显式并行

CampusFlow 可以为适合暂停后继续的任务保存正式执行画像，包括：

- 是否可拆分；
- 最小执行块；
- 偏好执行块；
- 是否要求一次完成；
- 画像来源。

因此同一个 `task_ref` 可以在多个真实可用窗口中出现多个执行块。例如 60 分钟作业可在
课程前完成 35 分钟、课程后继续 25 分钟。计划分配不会被当成实际完成，未完成工作仍由
原有任务进度台账保存；显式顺序、最小分块、地点离开边界和 fixed commitment 继续生效。

CampusFlow 默认不会在课程中主动塞入其他任务。只有用户明确授权某个任务与某个固定安排
同时执行时，系统才会创建绑定稳定 `task_ref` / `commitment_ref` 的并行授权，并由程序验证：

- 并行区间位于 commitment active interval 内；
- 任务与 commitment 地点兼容；
- 时长不超过任务剩余量；
- 普通 allocation 与 concurrent allocation 不会双重计时；
- 授权只对指定 pair 有效。

用户撤销并行后，授权会被删除，任务剩余量回到普通 planning；这不会等同于取消任务。

## 13. Agent Intelligence Layer

在结构化语义进入确定性规划后，CampusFlow 还会构造一个只读的
`AgentDecisionContext`。它不是第二份 source of truth，而是把当前时间、校区、任务、地点、
meal、fixed commitments、movement、并行授权、最近意图、当天偏好和当前方案整理成稳定、
可严格校验的 Qwen 决策视图。

一份复杂方案的智能决策链包括：

```text
canonical facts
    ↓
Situation Analyst
    ↓
Plan Strategist（2～4 个高层策略）
    ↓
程序生成并硬校验 deterministic candidates
    ↓
Plan Judge 选择一个候选
    ↓
Intent Compliance Reviewer 2.0
    ↓
Grounded Narrator
    ↓
Copy Fact Checker
    ↓
LiveFinalTurn atomic publish
```

Qwen 在这里负责理解情境矛盾、高层优先级、方案自然度和最新明确意图；分钟、路线、地点、
overlap、meal duration、class prep、并行可行性及最终发布仍由程序掌控。高层策略不能直接
修改硬事实，非法候选在交给 Plan Judge 前就会被淘汰。

这一层还包括：

- **Smart Clarification**：只在现有“待确认问题”区域显示最多一个高信息量问题；
- **What-if Preview**：在隔离副本中模拟“如果先吃饭呢”等假设，用户明确采用前不修改
  canonical state；
- **Day Preference**：只保存用户明确表达、仅当天有效的留白、饭点、碎片化和切换偏好；
- **Proactive Suggestion**：最多一条、先过稳定 ref 与确定性可行性检查，不会自动执行；
- **Grounded Narrator / Copy Fact Checker**：只读取最终候选，防止把 movement 目的地、
  planned / completed、meal / study 或 before / after 关系串错。

每个模型阶段默认调用一次，结构化解析失败最多修复一次，并有清晰的程序 fallback。
`AgentCallTrace` 只记录 stage、目的、成功/repair/fallback、可用的 latency/token metadata，
不保存 prompt、原始回复或密钥。普通 Streamlit rerun 继续复用完整 final turn，不调用模型。

前端仍只显示一份“当前方案”。内部候选、评分、置信度和推理过程不会出现在用户页面；
高价值说明继续收敛到右侧“温馨提示”，what-if 使用轻量预览卡，并行任务显示为主时间线
下的从属“同时”行。

## 14. 状态模型

CampusFlow 将“今天发生了什么”作为持续存在的状态，而不是每轮重新阅读聊天记录猜测。

当前核心状态包括：

### `DayPlanningState`

保存：

- 今日任务；
- fixed commitments；
- progress；
- 已完成 / 跳过 / 剩余任务；
- 可用时间窗口。

### `ExecutionPlanContext`

补充执行语义：

- task 与执行地点的绑定；
- activity kind；
- 有效任务时长；
- 时长来源；
- 当前地点；
- 当前地点来源 `user / assumed / unknown`；
- 需要确认的执行假设。

### `LiveFinalTurn`

保存同一 planning turn 中完整一致的最终结果。

renderer 读取完整 final turn，而不是从多个不同版本的 session snapshot 拼接页面。

这避免了：

- 旧 allocation；
- 新 movement；
- 旧 execution context；
- 新 presentation；

被错误混合到同一个页面中的问题。

---

## 15. 确定性安全边界

CampusFlow 对最终方案执行多项程序校验。

包括但不限于：

- task / movement / class prep / fixed commitment 不得时间重叠；
- 地点绑定任务不得在离开执行地点后继续；
- 课程准备时间不得被普通任务占用；
- 校区必须一致；
- 不支持偷偷跨校区规划；
- meal duration 必须满足当前正式策略；
- movement 与 destination 必须属于同一 final turn；
- candidate plan 必须通过最终一致性审计。

如果检测到结构冲突：

> **宁可不展示新的错误方案，也不把互相矛盾的时间线交给用户。**

## 16. 页面结构

当前 Streamlit 页面围绕一个核心输出：

## 当前方案

时间线会区分主要行动与辅助步骤。

主要行动例如：

- 步行；
- 学习；
- 写报告；
- 吃饭；
- 上课。

辅助步骤例如：

- 收拾东西；
- 进楼找教室；
- 课前准备；
- 修整一下。

辅助步骤使用更低的视觉权重，避免和真正需要用户关注的行动竞争注意力。

页面还可以根据当前状态动态显示：

- 温馨提示；
- AI 暂估标记；
- 自动食堂标签；
- 待确认问题。

不存在相关信息时，对应区域不会为了填满页面而强制出现。

主任务输入下方提供统一的“难以估计任务时间？让campusflow帮你估”草稿入口：

1. 写一句任务、粘贴通知或上传一张任务图片，补充会影响这份任务的个人情况；
2. 查看模型识别的任务范围、完成标准、专注用时范围与建议分钟数；
3. 如有需要，修正范围后重新估算，或直接修改最终采用的分钟数；
4. 点击“确认并加入计划”后，确认的工作量才会进入正式任务账本并重新规划。

估时草稿不会修改当前方案或实际完成进度。修改材料、范围或补充情况后，
必须重新估算才能加入；同一草稿重复点击也不会创建重复任务。估算只包含专注工作时间，
不包含通勤、休息和日程等待。图片请求继续复用正式消息适配；接口级能力通过后已开启，
但图片原件与Base64不进入本地档案或日志，复杂图片结果仍需用户确认。

### 临时使用与个人档案

CampusFlow 默认可以临时使用，不要求学号，也不会读取任何已保存的学生个人档案。
用户在“个人设置”中明确开启个性化、输入学号后，任务、实际进度、可靠方案、文字
估时草稿、偏好、常用地点和课表会按内部 `user_id` 隔离保存。重新打开页面时，再
输入同一学号即可选择对应档案。

**学号唯一，但不是身份认证。** 它在当前版本只用于本地档案映射，不会发给 Qwen，
也不能作为公开公网服务的安全登录方式。本版适合本地或可信小范围试用。

Windows 默认数据位置为 `%LOCALAPPDATA%\CampusFlow\campusflow.sqlite3`；Linux
服务器应使用 `CAMPUSFLOW_DATA_DIR` 指定源码目录之外的持久目录。保存采用版本化
SQLite 记录，不写入 API Key、模型客户端、完整提示词、调用轨迹或上传图片。详细
部署边界见 `docs/deployment_readiness.md`；公开资料与公网缺口见
`docs/public_test_readiness.md`；已经离线跑通的外部身份映射、版本实验和测试版认证建议
见 `docs/authentication_prototype.md`。当前学号仍只是可选档案资料。外部认证使用
provider 的稳定 `sub` 创建独立映射，再进入内部 `user_id`，学号不决定认证结果。

测试服务器可复用仓库中的示例：

- `deploy/campusflow.service.example`：单进程、非 root 的 systemd 服务；
- `deploy/nginx-campusflow.conf.example`：HTTPS、WebSocket 和外置 OIDC 网关接线示例；
- `deploy/streamlit-oidc.secrets.toml.example`：未来 Streamlit 1.45+ 原生 OIDC 配置形状；
- `deploy/campusflow.env.example`：不含真实值的环境变量清单；
- `scripts/server_readiness.py`：检查 Streamlit 就绪端点；
- `scripts/sqlite_profile_backup.py`：用 SQLite 在线备份 API 生成并校验快照。

测试版收集内容与模型数据边界见 `docs/test_data_notice.md`。这些模板不等于已经完成
公网认证或部署，也不包含真实域名、密钥、服务器地址或用户标识。

认证映射使用 SQLite schema v4。v3 会原地增量创建身份关联表，不重写已有档案；
provider token 不保存。正式依赖仍是 Python 3.8.10 + Streamlit 1.31.1，因此默认入口
尚未启用真实 OIDC。仓库里的离线认证演示使用合成 Alice/Bob 身份，只验证档案映射、
隔离、退出与恢复，不代表真实第三方登录已经配置。

重新打开页面或重启本地服务时，读取本机记录不会调用模型，也不会自动重新估时或
重新规划。已经过时的方案会标为“上次保存的方案”，保留原参考时间；跨日记录只供
查看，不会把昨天的课程、位置、偏好或并行授权自动复制到今天。时间经过也不会增加
任务的实际完成进度。

旧版单用户数据升级后保留在 `legacy-local` 档案，不会静默绑定任何真实学号。用户
可以在设置中明确选择把它复制到一个空的个人档案。损坏、版本不兼容或同档案旧页面
revision 冲突时，程序保留原文件，不会静默清空或跨档案覆盖。

页面右上角的“个人设置”使用同一份本机 SQLite 档案保存长期默认，包括常用出行
方式、学习节奏、午晚饭偏好时段、用户原话补充、分校区常用地点和手动课表。面板
编辑先保留为草稿，只有点击“保存设置”才生效；保存不会自动调用模型或重排当前
方案，需由用户随后明确更新。课表按规划日期、教学周和单双周展开为当天固定安排，
地点仍严格受所选校区约束。数据库不会保存模型密钥、完整提示词、上传图片或整个
Streamlit 会话状态。

在“个人设置 → 我的课表”中还可以粘贴一段包含多门课程的课表文字。只有点击
“识别课表”时才会调用一次当前模型服务；若回复格式无法解析，最多再做一次格式
修复。识别结果先进入可编辑预览，缺少实际起止钟点、教学周或校区的课程会明确
标为待补，不会根据“第3—4节”猜学校作息。确认导入时，程序再校验冲突、精确重复
和稳定引用，并与个人设置一起原子保存；解析成功本身不会自动修改课表或当前方案。

页面视觉使用天津大学公开标识资料中记载的“北洋蓝”作为产品配色灵感，但代码中的
具体色值是 CampusFlow 为可读性自行调配的产品色，不冒充学校 VI 标准色。品牌区的
路径图形为原创装饰，不是校徽或真实校园地图。CampusFlow 是独立产品，不冒充学校
官方教务系统。

## 22. 当前边界

CampusFlow 当前聚焦于：

> **大学生校园场景下，从现在开始应该做什么。**

它目前并不试图成为：

- 通用 Todo 软件；
- 完整日历系统；
- 企业项目管理软件；
- 分钟级行为控制器；
- 全城市导航；
- 跨校区交通规划平台；
- 所有大学通用的校园地图产品。

当前校园地图仅针对已经构建的数据范围。

跨校区 route 不会被程序偷偷猜测。

一些现实世界信息，例如：

- 食堂实时营业状态；
- 建筑实时开放状态；
- 教室实时占用；
- 校园道路临时封闭；

目前也不属于静态地图可以保证的事实。

---

## 23. 设计目标

CampusFlow 最终希望做到的并不是：

> “让 AI 替用户把一天塞满。”

而是：

> **让 Agent 理解用户现在的现实状态，在校园时间、地点和任务约束下，给出下一步真正可以执行的建议。**

系统允许留白，也允许计划改变。

计划不是目的。

> **帮助用户在真实变化发生以后，仍然知道下一步做什么，才是 CampusFlow 的核心。**
